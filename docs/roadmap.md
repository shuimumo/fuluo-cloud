# 福洛社区 · V2.0 前路线图（V1.1 → V1.3）

> 定位：**泛兴趣社区**。游戏是首批内容类目之一，不作为唯一维度；话题/兴趣分类承担内容组织职责。
> 代码主线：**本仓库**（12 个 Maven 模块的微服务实现）。单体版本在独立的 `monolith` 仓库，冻结在与本仓库功能对等的版本，
> 只接受安全与紧急缺陷修复，不再叠加新功能。

## 0. 交付原则

1. **一个版本一次上线**：每 2–3 周一个可上线版本，版本内需求可独立回滚（开关或独立接口）。
2. **先闭环、再增长**：举报/删除/处罚/审核反馈属于「社区能自我治理」的底线，优先于增长功能。
3. **验收口径先写**：每个需求必须给出可验证的验收条件与对应埋点事件，否则不排期。
4. **质量门槛**：`mvn -T 1C clean package -DskipTests` 通过；关键链路手工冒烟
   （注册/登录 → 发帖 → 审核 → 列表/详情 → 通知 → 搜索 → 举报 → 后台处置）。
5. **不做的事**：V1.x 内不做私信、不做推荐算法、不做会员/联运（数据量不足，先攒样本）。

## 1. V1.1 社区治理与基础闭环（2 周）

目标：让用户「能被保护、能申诉」，让运营「能处置、能看见」。

| # | 需求 | 落点模块 | 验收口径 |
|---|------|----------|----------|
| 1.1 | 举报与申诉闭环 | 新表 `report`（fuluo-common-data）；举报入口在 fuluo-post / fuluo-comment / fuluo-user；处理队列与操作留痕在 fuluo-admin；结果通知走 fuluo-notification（新增 `REPORT_RESULT`） | 可举报帖子/评论/用户；后台按状态筛选、填写处理结论；举报人在消息中心收到结果；同一用户对同一目标重复举报被限频 |
| 1.2 | 评论自助删除 | fuluo-comment 新增 `DELETE /comment/{id}`；同步 post.comments 计数、评论 ZSET、缓存、被回复人通知 | 作者可删、他人 403；删除后详情页与计数一致；被删评论不再出现在回复列表 |
| 1.3 | 后台用户处置 | fuluo-admin 用户列表 + 禁言/封禁/解封；fuluo-user 校验 `status` 与禁言截止时间（登录、发帖、评论、点赞拦截）；操作日志 | 禁言用户发帖/评论返回明确提示；到期自动恢复；每次处置有操作人与原因 |
| 1.4 | 审核体验 | fuluo-post/comment 详情返回审核状态与预计时延；fuluo-notification 拆出「审核结果」独立分类；拒绝原因模板化 | 发布后可见「审核中」卡片；结果通知单独可查；拒绝原因不再是平台原始文案 |
| 1.5 | 数据看板 v0 + 埋点 | fuluo-admin Dashboard 接真实指标（DAU、发帖、评论、待审积压、审核 P90）；前端事件上报（注册/发帖/评论/点赞/搜索） | 5 个指标当日可查；事件表能算出 DAU 与发帖漏斗 |

依赖顺序：1.1 与 1.3 共用「处置动作」模型；1.4 的审核结果分类复用 1.1 的通知扩展；1.5 最后做（收集前面产生的数据）。

## 2. V1.2 内容沉淀与分发（3 周）

目标：让好内容「存得下、找得到、传得开」。

| # | 需求 | 落点模块 | 验收口径 |
|---|------|----------|----------|
| 2.1 | 收藏 | `favorite` 表已存在，缺接口与入口：fuluo-post 收藏/取消 + 我的收藏列表；收藏数进热度权重；联动「收藏公开」隐私开关 | 收藏/取消幂等；个人主页有「收藏」tab；他人不可见私密收藏 |
| 2.2 | 分享 | `post.shares` 字段已存在：站内转发（引用原帖生成新帖）、复制链接、分享数统计 | 分享数正确累加；转发帖带原帖引用与作者 |
| 2.3 | 草稿箱 | fuluo-post 新增草稿状态（不进榜单、不发通知、不计入统计）+ 自动保存 + 我的草稿 | 刷新/断网不丢内容；草稿仅本人可见；可一键发布 |
| 2.4 | 搜索多域 | fuluo-search 扩展用户/话题索引，`GET /search?type=` 支持帖子/用户/话题；搜索历史与热词 | 三域结果分栏；无结果有引导；历史与热词可点 |
| 2.5 | 评论体验 | 排序（时间/热度）、@提及、回复通知细分（回复评论 vs @我）、楼中楼折叠 | @ 产生通知；排序切换生效；折叠不影响回复数 |
| 2.6 | 主页与关注 | bio/背景图、认证标识（大V/官方）、互关标识、关注话题、首页「推荐」tab（规则：关注 + 话题 + 热度加权） | 主页信息完整；互关可见；推荐 tab 冷启动有兜底内容 |

## 3. V1.3 运营与增长（3 周）

目标：让运营「有抓手」、让用户「有理由回来」。

| # | 需求 | 落点模块 | 验收口径 |
|---|------|----------|----------|
| 3.1 | 兴趣分类 / 话题广场 | 一级分类（游戏、二次元、数码、生活…）+ 话题发现页 + 关注话题 | 分类页可浏览；关注话题内容进 inbox |
| 3.2 | 内容运营位 | 置顶、加精、话题运营位、站内推送（站内信，复用通知队列） | 后台可操作；置顶在列表首位；推送可按人群 |
| 3.3 | 轻量成长体系 | 积分（发帖/评论/获赞）+ 等级 + 徽章；积分流水可查 | 等级展示在主页/评论；无刷分漏洞（限频、去重） |
| 3.4 | 榜单 | 用户榜、话题榜、周榜（复用 ZSET + 定时任务） | 榜单可刷新、口径可解释 |
| 3.5 | 留存看板 | 漏斗：注册 → 发帖 → 首评 → 7 日回访；留存曲线 | 可看次日/7 日留存与转化率 |
| 3.6 | 通知偏好 | 免打扰时段、按分类订阅 | 设置立即生效 |

## 4. V2.0（本期不实现，先留接口）

- **游戏库 / 游戏专区 / 评分攻略**：仅在游戏类目数据验证成立后启动；V1.x 的分类与话题结构需预留 `category_id`。
- 私信、推荐算法、会员与联运：均需内容量与用户量支撑，V1.x 只保证数据结构可扩展（不建表、不做半成品）。

## 5. 里程碑与并行度

| 版本 | 周期 | 可并行工作 |
|------|------|-----------|
| V1.1 | 2 周 | 举报/申诉（后端）+ 后台处置（后端）+ 审核体验/通知分类（后端）；看板最后 3 天 |
| V1.2 | 3 周 | 收藏 + 分享（同一批表结构改动）；草稿独立；搜索多域依赖 ES 索引扩展，可提前一周启动 |
| V1.3 | 3 周 | 分类/话题广场先行（数据结构决定后续运营位）；成长体系与榜单共用统计任务 |

## 6. 指标口径

- **北极星**：周活跃创作者数（当周发帖或评论 ≥1 的去重用户）。
- 辅助：次日留存、7 日留存、发帖→首评率、审核 P90 时延、举报平均处理时长、收藏率（收藏/浏览）。
- 每个需求上线前必须能在看板看到对应事件；看不到事件视为未完成。

## 7. 风险与对策

| 风险 | 对策 |
|------|------|
| 举报滥用/恶意举报 | 举报限频、被举报方通知、后台一键驳回 + 举报人信誉分 |
| 跨服务一致性（删评论要动计数/ZSET/通知） | 以「DB 为真相 + MQ 补偿 + 幂等 eventId」为统一模式，复用现有 dirty/重试机制 |
| 审核成本（阿里云按量计费） | 保持批量消费 + 人工兜底；高风险用户/新用户优先全量审核 |
| 单体与微服务漂移 | monolith 冻结，仅安全补丁；文档与 CI 均以 cloud 为准 |
| 范围膨胀 | V1.x 明确不做私信/推荐/会员；V2.0 需求需重新评审 |
